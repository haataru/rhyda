# 04. Performance Architecture

This document describes the high-throughput design of RhydaDB: the network
pipeline, the sharded storage engines, the durability pipeline, tunables, and
measured throughput.

## 1. Network layer (server.rs)

- **True CQL pipelining.** Every QUERY/EXECUTE frame is dispatched to its own
  tokio task; responses are written as they complete, possibly out of order —
  the native protocol v4 correlates them by stream id, exactly like Cassandra.
  Throughput is no longer bound to `connections × (1/RTT)`.
- **TCP_NODELAY** on every socket; `BufReader` (64 KB) on the read side; a
  dedicated writer task coalesces ready responses into `write_vectored` calls
  (flush threshold 256 KB).
- **Lock-free hot path.** Per-connection state uses fine-grained primitives:
  compression is an `AtomicU8`, the prepared-statement map and session
  keyspace are `RwLock`s touched only by PREPARE/STARTUP/USE. EXECUTE never
  blocks on a connection-level mutex.
- Control-plane opcodes (STARTUP/OPTIONS/REGISTER/PREPARE and text `USE ...`
  queries) execute inline on the reader task so ordering semantics are kept:
  a PREPARE is registered before any later EXECUTE of its id can arrive, and
  USE is applied before subsequent statements observe the session keyspace.
- In-flight requests per connection are capped (512) by a semaphore.

## 2. Sharded storage engines (storage.rs)

RhydaDB runs **N independent RocksDB instances** ("engines", default
`min(cpus, 8)`, configurable up to 64), ScyllaDB-style:

- A row's engine is `hash("dt!<keyspace>!<table>!" + first partition-key part)
  % N` — every row of a partition always lives on the same engine, so
  intra-partition scans keep clustering order and never fan out.
- Each engine has its own memtable, WAL, block-cache share and compaction
  threads. Writes no longer serialize on one global memtable mutex — this is
  what lifted sustained writes from ~350 K to ~870 K ops/s on the test box.
- Metadata (`ks!`/`tb!` prefixes and system tables) always lives on engine 0.
- The shard count is persisted in `<data>/ENGINE-SHARDS` on first start;
  restarts reuse it so rows are never misrouted. Changing the value requires
  an empty data directory.
- DDL and schema metadata writes are **always synchronous** (`set_sync(true)`
  in durable mode): CREATE/DROP/TRUNCATE complete before their acknowledgement
  and are immediately visible, independent of async data-write pipelines.
- DROP KEYSPACE / TRUNCATE use O(1) range tombstones (`WriteBatch::delete_range`)
  across all engines instead of per-row deletes — dropping a billion-row
  keyspace no longer floods the write path.

## 3. Durability modes

| Mode | Data writes | Durability | Read-after-write |
|---|---|---|---|
| default (`RHYDADB_SYNC` unset) | direct concurrent puts, WAL disabled | memtable flushes only; process crash may lose recent seconds | strict |
| `RHYDADB_SYNC=set` | sharded group commit: per-engine collector drains ops into rotating WriteBatch buffers (up to 1024 ops) while a dedicated committer performs `set_sync(true)` writes; the collector never blocks on disk | fsync per batch (~1024 ops) | data windowed (µs–ms, Cassandra `ONE`-like); metadata strict |

The "rotating buffers" pipeline means writers keep flowing while fsync runs —
there is no stop-the-world phase. Because one fsync amortizes over ~1024
operations, enabling durability costs little throughput (see benchmarks).

## 4. RocksDB tuning applied

- Block-based options: shared LRU block cache (`RHYDADB_CACHE_MB`, default
  1024 MB), 16 KB blocks, Bloom filters (10 bits/key), index/filter blocks
  cached and pinned.
- Memtable: `RHYDADB_MEMTABLE_MB` (default 128 MB) × 6 buffers, merge 2.
- `increase_parallelism`/`max_background_jobs` scaled per engine count,
  leveled-compaction optimizer enabled, LZ4 compression.
- `allow_concurrent_memtable_write`, adaptive write-thread yield.

## 5. Environment variables

| Variable | Default | Meaning |
|---|---|---|
| `RHYDADB_DATA` | `./data` | Data directory (**keep out of OneDrive/Dropbox and antivirus-scanned paths**) |
| `RHYDADB_LISTEN` | `127.0.0.1:9042` | Bind address |
| `RHYDADB_SYNC` | unset | Durable mode: sharded fsync group commit |
| `RHYDADB_ENGINE_SHARDS` | `min(cpus, 8)` | Number of independent RocksDB instances (persisted on first start, max 64) |
| `RHYDADB_CACHE_MB` | `1024` | Shared block cache size |
| `RHYDADB_MEMTABLE_MB` | `128` | Per-engine write-buffer size |
| `RHYDADB_MANUAL_WAL` | unset | Opt-in manual WAL buffering (non-durable mode) |

## 6. Benchmark results

Client: `src/bin/bench.rs` — raw CQL v4 frames, prepared statements, N
connections × M pipelined EXECUTEs, uniform random keys over 1M space.
Test box: 20-core/28-thread desktop, NVMe SSD.

Windows native (`C:\temp`, **not** inside OneDrive — see warning below),
8 engine shards:

| Workload | Baseline (pre-upgrade) | After upgrade |
|---|---|---|
| READ 32×256 | 213 K ops/s | **1 410 K ops/s** |
| WRITE 15 s (non-durable) | 719 K peak / ~340 K sustained | **875 K ops/s sustained** |
| MIXED 16×256 | 52 K ops/s (flush-gate collapse) | **1 420 K ops/s** |
| WRITE (durable, fsync group commit) | — | 575–863 K ops/s |

Docker Desktop (Ubuntu 24.04 image, WSL2 kernel 6.18, 28 CPUs):

| Workload | Throughput |
|---|---|
| READ 32×256 | **2 190 K ops/s** |
| WRITE 15 s (non-durable) | 433 K ops/s |
| WRITE (durable, fsync group commit) | 419 K ops/s |

Notes:
- Above ~1.5–2 M ops/s the single-process benchmark client itself becomes the
  bottleneck on Windows loopback; Linux numbers scale further.
- Baseline WRITE benefited from batched channel writes but ran inside a
  OneDrive-synced directory (see below); sustained baseline degraded to
  ~340 K within seconds once compaction started.

### Storage-location warning (Windows)

Never point `RHYDADB_DATA` into a OneDrive/Dropbox-synced folder or an
antivirus-scanned path without exclusions. Measured impact on this test box:
**86 K vs 341 K sustained writes** (≈4×) purely from sync/scan overhead on new
SST files, plus periodic multi-second stalls. Prefer `C:\rhydadb-data` style
paths or add a Defender exclusion for the data directory.

## 7. io_uring roadmap (Linux)

The transport today is tokio (IOCP on Windows, epoll on Linux). On Linux the
next step is an io_uring-backed, thread-per-core transport (`monoio` or
`tokio-uring`) behind a cargo feature:

```
cargo build --release --features uring   # Linux only
```

Design sketch: one reactor thread per core owns its acceptor and connection
set; sockets, file IO and timers all go through a single io_uring ring per
thread — zero cross-thread wakeups on the hot path. The storage layer needs
no change: pin each connection to the engine matching its partition hash and
the common case stays thread-local.

Running under Docker requires io_uring syscalls to be permitted; the default
seccomp profile blocks them:

```sh
docker run --security-opt seccomp=unconfined ...
# or supply a profile that whitelists io_uring_setup/io_uring_enter/io_uring_register
```

## 8. Measurement methodology

Fresh data directory per series; 15 s warm-up runs discarded; compaction debt
drained (≥10 s idle) between write and read phases; every number in this
document is the mean of a ≥10 s steady-state run with errors = 0. Reproduce
with:

```sh
cargo build --release
./target/release/rhydadb &                    # RHYDADB_DATA outside synced folders!
./target/release/bench --mode write --conns 32 --pipeline 256 --seconds 15
./target/release/bench --mode read  --conns 32 --pipeline 256 --seconds 10
```
