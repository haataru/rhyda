# 04. Performance Architecture

This document describes the high-throughput design of RhydaDB: the network pipeline (tokio and monoio thread-per-core), sharded storage engines, durability pipeline, row-cache, tunables, and measured throughput. All numbers are from `bench_async` (tokio async client, prepared statements, uniform random keys over 1M space) unless noted.

## 1. Network Layer

### Tokio (default, all platforms)

- **True CQL pipelining.** Every `QUERY`/`EXECUTE` frame is dispatched to its own tokio task; responses are written as they complete, possibly out of order — the native protocol v4 correlates them by stream id, exactly like Cassandra. Throughput is no longer bound to `connections × (1/RTT)`.
- **TCP_NODELAY** on every socket; `BufReader` (64 KB) on the read side; a dedicated writer task coalesces ready responses into `write` calls (flush threshold 256 KB).
- **Lock-free hot path.** Per-connection state uses fine-grained primitives: compression is an `AtomicU8`, the prepared-statement map and session keyspace are `RwLock`s touched only by `PREPARE`/`STARTUP`/`USE`. `EXECUTE` never blocks on a connection-level mutex.
- Control-plane opcodes (`STARTUP`/`OPTIONS`/`REGISTER`/`PREPARE` and text `USE ...` queries) execute inline on the reader task so ordering semantics are kept: a `PREPARE` is registered before any later `EXECUTE` of its id can arrive, and `USE` is applied before subsequent statements observe the session keyspace.
- In-flight requests per connection are capped (512) by a semaphore.

### Monoio thread-per-core (Linux, feature `uring`)

Enabled with `RHYDADB_URING=1` and `cargo build --release --features uring` (Linux only, requires `liburing-dev` and `seccomp=unconfined` in Docker):

```
cargo build --release --features uring   # Linux only
RHYDADB_URING=1 ./target/release/rhydadb
docker run --security-opt seccomp=unconfined -e RHYDADB_URING=1 -p 9042:9042 rhydadb:uring
```

Design: `N = cpus` (or `RHYDADB_URING_THREADS`) `monoio::FusionDriver` runtimes, each with a `SO_REUSEPORT` listener. No cross-thread wakeups on the hot path: each core owns its acceptor and connection set. `Storage` is shared via `Arc` (still sharded RocksDB), but the common single-PK point lookup stays thread-local. Cross-thread wakeups only happen for `oneshot` completion of group-commit batches (`sync` feature for `monoio` wakers).

Measured gain in Docker Desktop (WSL2 6.18, 28 vCPUs): `+11%` read over tokio on the same image (see §6).

## 2. Sharded Storage Engines (storage.rs)

RhydaDB runs **N independent RocksDB instances** ("engines", default `clamp(cpus, 4..16)`, configurable up to 64, persisted in `<data>/ENGINE-SHARDS`), ScyllaDB-style:

- A row's engine is `hash("dt!<keyspace>!<table>!" + first partition-key part) % N` — every row of a partition always lives on the same engine, so intra-partition scans keep clustering order and never fan out.
- Each engine has its own memtable, WAL, block-cache shard and compaction threads. Writes no longer serialize on one global memtable mutex — this is what lifted sustained writes from ~350 K to >1 M ops/s on the test box.
- Metadata (`ks!`/`tb!` prefixes and system tables) always lives on engine 0.
- The shard count is persisted on first start; restarts reuse it so rows are never misrouted. Changing the value requires an empty data directory.
- DDL and schema metadata writes are **always synchronous** (`set_sync(true)` in durable mode): `CREATE`/`DROP`/`TRUNCATE` complete before their acknowledgement and are immediately visible, independent of async data-write pipelines.
- `DROP KEYSPACE` / `TRUNCATE` use O(1) range tombstones (`WriteBatch::delete_range`) across all engines instead of per-row deletes — dropping a billion-row keyspace no longer floods the write path.

### Phase 2: Row Cache

`RHYDADB_ROW_CACHE_ENTRIES` (default `500_000`, `0` to disable) — `DashMap`-based point-lookup cache keyed by full `dt!` key (`[DT_PREFIX + keyspace + table + encoded key]`), storing raw RocksDB value bytes. Write-through on `put_row`/`put_row_sync`, invalidate on `delete_row`/`delete_data_prefix` (`DROP`/`TRUNCATE` clears). Skips `system`/`system_schema`. For the bench working set (`200k` keys) the cache fits entirely and turns point reads into a single `DashMap::get` (no `DB::get`, no Bloom, no block-cache search). Measured `+14%` read on Windows (`32×128` `1.12M → 1.29M`), larger on Linux where `DB::get` is more expensive.

Fast point-lookup path (`query.rs`): single-PK `EQ`-only point lookups (`bench.kv` pattern) avoid allocating the full `Vec<Value>` row vector and filter re-check. The output row is built by scanning the sparse `value_bytes` only for the `selected` indexes — `+20%` on `32×128` (`1.27M → 1.53M` on the same Windows box).

## 3. Durability Modes

| Mode | Data writes | Durability | Read-after-write |
|---|---|---|---|
| default (`RHYDADB_SYNC` unset) | micro-batched: per-engine collector drains concurrent ops into `WriteBatch` buffers, committer applies them WAL-less | memtable flushes only; process crash may lose recent ops | strict — responses are gated on commit |
| `RHYDADB_SYNC=set` | same pipelines, committer fsyncs each batch; collector holds the batch open ≤1 ms to merge synchronized client waves into fewer, larger fsyncs | fsync per batch (up to 2048 ops) | strict — gated on the fsync'd commit |

Both modes run identical "rotating buffer" pipelines: a per-engine collector thread never blocks on disk while its committer performs the write. Every data write carries an individual oneshot completion channel; the server awaits it before sending the response. One commit wakes exactly the tasks waiting on that batch — no broadcast herds, no blocked worker threads.
Metadata (`ks!`/`tb!`, `system_schema` mirrors) always bypasses the pipelines: synchronous and immediately visible. `DROP`/`TRUNCATE` range tombstones are routed through the pipelines so they can never overtake queued row ops.

## 4. RocksDB Tuning Applied

- Block-based options: shared LRU block cache (`RHYDADB_CACHE_MB`, default `1024 MB`), 16 KB blocks, Bloom filters (10 bits/key), `cache_index_and_filter_blocks` and `pin_l0_filter_and_index_blocks_in_cache` true.
- Memtable: `RHYDADB_MEMTABLE_MB` (default `128 MB`) × 6 buffers, `level_style_compaction` (2), `max_write_buffer_number=6`, `min_write_buffer_number_to_merge=2`.
- `increase_parallelism(cpus)`, `max_background_jobs = cpus / shards` clamped `2..8`, `optimize_level_style_compaction`, LZ4 compression.
- `allow_concurrent_memtable_write = true`, `enable_write_thread_adaptive_yield = true`, `enable_pipelined_write = true` (phase 1).
- Global allocator `mimalloc` (phase 1) — `+15%` on `bench_async` vs system allocator for `Value`/`RocksDB` heavy allocations.

- `bench` — classic OS-thread-per-connection client;

#### Bare-Metal Linux (Expected, not WSL2)

WSL2 virtual disk caps throughput: write `1.31 M → 0.72 M` non-durable and `160 K` durable in docs vs `1.20 M` native; read `1.75 M Windows → 2.27 M Docker` before, now `4.01 M` in Docker. On bare-metal Linux (NVMe, no virtualization, `ext4` + `O_DIRECT` for WAL in future) the same binary is expected to exceed **5 M read** and sustain **>1 M write** (`tokio` already `3.6 M` in VM, `io_uring` adds `+11%`; removing WSL2 overhead historically `+30%`). This is the target for Phase 3 bare-metal validation.

### Storage-Location Warning (Windows)

Never point `RHYDADB_DATA` into a OneDrive/Dropbox-synced folder or an antivirus-scanned path without exclusions. Measured impact on this test box: **86 K vs 341 K sustained writes** (≈4×) purely from sync/scan overhead on new SST files, plus periodic multi-second stalls. Prefer `C:\rhydadb-data` style paths or add a Defender exclusion for the data directory.

## 7. Thread-Per-Core io_uring (Linux, Phase 3)

The transport today is `tokio` (IOCP on Windows, `epoll` on Linux) by default. On Linux the next step is a `io_uring`-backed, thread-per-core transport (`monoio::FusionDriver`) behind a cargo feature (now implemented):

```
cargo build --release --features uring   # Linux only, needs liburing-dev
RHYDADB_URING=1 RHYDADB_URING_THREADS=28 ./target/release/rhydadb
docker build -t rhydadb:uring .   # Dockerfile already does --features uring
docker run --security-opt seccomp=unconfined -e RHYDADB_URING=1 -p 9042:9042 rhydadb:uring
```

Design: one `FusionDriver` per core (`with_entries(16384)`, `enable_timer`), each owns its `SO_REUSEPORT` acceptor and connection set; sockets, file IO and timers all go through a single `io_uring` ring per thread — zero cross-thread wakeups on the hot path (`async_channel` for responses, `tokio::sync::Semaphore` with `sync` feature for per-conn inflight). The storage layer needs no change: `Arc<Storage>` is shared, but the common point-lookup is already `DashMap`-cached and thread-local.

Running under Docker requires `io_uring` syscalls to be permitted; the default `seccomp` profile blocks them:

```sh
docker run --security-opt seccomp=unconfined ...
# or supply a profile that whitelists io_uring_setup/io_uring_enter/io_uring_register
```

## 8. Measurement Methodology

Fresh data directory per series; `15 s` warm-up runs discarded; compaction debt drained (`≥10 s` idle) between write and read phases; every number in this document is the mean of a `≥8 s` steady-state run with `errors = 0`. Reproduce with:

```sh
cargo build --release --features uring  # Linux: uring, Windows: tokio
./target/release/rhydadb &                    # RHYDADB_DATA outside synced folders!
./target/release/bench_async --mode write --conns 64 --pipeline 128 --seconds 10 --keys 1000000
./target/release/bench_async --mode read  --conns 64 --pipeline 128 --seconds 8 --keys 1000000 --fill-keys 200000
# Docker (WSL2):
docker build -t rhydadb:uring .
docker run -d --name rhydadb --security-opt seccomp=unconfined -p 9042:9042 -e RHYDADB_URING=1 rhydadb:uring
docker exec rhydadb timeout 10 /usr/local/bin/bench_async --addr 127.0.0.1:9042 --mode read --conns 64 --pipeline 128 --seconds 8
```
