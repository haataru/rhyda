# 03. Storage Engine Architecture

RhydaDB runs **N independent RocksDB instances** ("engines", default `clamp(cpus, 4..16)`, max 64, persisted in `<data>/ENGINE-SHARDS`) and distributes rows across them by partition hash — ScyllaDB-style sharding on a single node. The storage layer owns the on-disk layout, schema/AST/row caches, the micro-batched write pipelines, and exposes a small API used by the query engine.

## Core Concepts

1. **Three key namespaces** — `ks!` for keyspace metadata, `tb!` for table definitions, `dt!` for row data; all keys are lexicographically ordered byte strings. Metadata always lives on engine 0.
2. **Partition-hashed routing** — a row's engine is `hash("dt!<keyspace>!<table>!" + first partition-key part) % N`. Every row of a partition lands on the same engine: point lookups, partition scans and intra-partition clustering order never cross engines.
3. **Micro-batched writes with completion tickets** — data writes flow through per-engine pipelines that coalesce concurrent operations into `WriteBatch` buffers; callers receive a ticket they must await before acknowledging.
4. **Point-lookup row cache (phase 2)** — `DashMap` keyed by full `dt!` key, storing raw RocksDB value bytes, write-through on `put_row`/`put_row_sync`, invalidate on `delete_row`/`delete_data_prefix` (`clear()` on `DROP`/`TRUNCATE`), opt-out via `RHYDADB_ROW_CACHE_ENTRIES=0` (default `500_000`). Skips `system`/`system_schema`. Turns hot point reads into a single `DashMap::get` when working set fits — `+14%` on `32×128` in the benchmark.
5. **Synchronous metadata** — DDL, schema mirrors and system rows bypass the pipelines entirely: synchronous, immediately visible, durable.
6. **Persisted layout** — the engine count is written to `<data>/ENGINE-SHARDS` on first start; restarts reuse it so rows are never misrouted.

## Key Layout

- `ks!<name>` — `KeyspaceDef` serialized as JSON (engine 0).
- `tb!<keyspace>!<table>` — `TableDef` as JSON (engine 0).
- `dt!<keyspace>!<table>!<pk1>[!<ck1>...]` — row data (routed engine). Key
  parts are length-prefixed (`u16 BE` + bytes, `encode_key`); `decode_key`
  reverses them.
- Row values are sparse: `[idx u16 BE][wire value]` per non-null regular
  column (`encode_row_columns` / `decode_row_columns`); a length of `-1` marks
  null. Partition and clustering key columns live only in the key.

## Write Pipelines

Each engine has one collector thread and one committer thread:

```
put_row/delete_row ──► mpsc ──► collector ──(batch, done[])──► committer ──► RocksDB
   ▲                             drains ops into               write_opt +
   └── caller awaits oneshot      rotating WriteBatch           drops senders
       completion channel         buffers (≤2048 ops)           ⇒ waiters wake
```

- The collector never blocks on disk; it keeps draining while the committer
  writes ("no stop").
- Non-durable mode: batches are committed immediately (`disable_wal`), so the
  memtable lock is amortized over a whole batch instead of per request.
- Durable mode (`RHYDADB_SYNC`): the collector holds a fresh batch open for up
  to 1 ms to merge synchronized client waves, then the committer performs one
  fsync'd write per batch — up to 2048 operations per fsync.
- Completion signalling is individual: each op carries an optional
  `oneshot::Sender`; the committer drops the senders after its batch commits,
  waking exactly the tasks waiting on that batch. No broadcast herds.
- DROP KEYSPACE / TRUNCATE enqueue `DeleteRange` tombstones through the same
  pipelines (one per engine) so they can never overtake queued row ops;
  O(1) regardless of table size.
- On drop, Storage closes the pipeline inputs and joins all threads: every
  accepted write is committed before the directory is released.

## Read Path

- Point reads: `DashMap` row-cache lookup first (if enabled and not `system`/`system_schema`), otherwise one `get` on the routing engine (bloom filter + block cache). On `DB::get` miss the result is inserted into the cache. The query layer's fast single-PK point path (`02`) then builds the output row by scanning the sparse `value_bytes` only for the `selected` indexes, without the full `Vec<Value>` allocation.
- Partition scans: forward iterator from the partition prefix on the owning engine, callback-based with early termination (`for_each_in_partition`).
- Full scans: sequential iteration across engines (`for_each_in_table`).
- Reads never wait on writers; visibility is guaranteed by response gating in the server layer (see `01`). Row-cache is write-through, so a just-committed `put` is immediately visible even before the `WriteBatch` hits the memtable.

## Schema & AST Caches

- `RwLock<HashMap>` over keyspaces and `Arc<TableDef>` tables: cache hits are
  zero-copy `Arc` clones; a miss performs one RocksDB read plus JSON
  deserialization. Lookups compare keys without allocating.
- DDL updates RocksDB synchronously and swaps cache entries atomically.
- The AST cache (see 02) is owned here and invalidated wholesale at capacity.

## Durability Modes

| Mode | Data writes | Crash window |
|---|---|---|
| default | WAL disabled, micro-batched straight to the memtable | until next memtable flush |
| `RHYDADB_SYNC=set` | fsync per batch (up to 2048 ops), 1 ms accumulation window | at most one un-fsynced batch |

Metadata is always written synchronously (`set_sync(true)` in durable mode).

## RocksDB Tuning

Per engine: LZ4 compression, leveled compaction (`optimize_level_style_compaction`) with parallel background jobs (`max_background_jobs = cpus / shards` clamped `2..8`), memtable `RHYDADB_MEMTABLE_MB` (default 128 MB) × 6 buffers, shared LRU block cache `RHYDADB_CACHE_MB` (default 1024 MB), 16 KB blocks, Bloom filters (10 bits/key), pinned index/filter blocks, `allow_concurrent_memtable_write=true`, `enable_write_thread_adaptive_yield=true`, `enable_pipelined_write=true` (phase 1), global allocator `mimalloc` (phase 1).
